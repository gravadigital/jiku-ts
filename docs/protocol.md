# The protocol

What actually travels on the bus. The source of truth is the deployment's AsyncAPI contracts;
this describes what this client does with them and why.

## Subjects

```text
{instance}.{userId}.{service}.{version}.{method}
dev.275649063808925701.jiku-queries.v1.tasks.list
```

| Token      | What it is                                         |
| ---------- | -------------------------------------------------- |
| `instance` | the deployment: `dev` or `prod`                    |
| `userId`   | **the Zitadel token's `sub`, raw**                 |
| `service`  | `jiku-queries` or `jiku-commands`                  |
| `version`  | `v1`                                               |
| `method`   | `tasks.list`, `requirements.7.subscriptors.new`, … |

The user id travels **raw and unhashed**, and that is the point: the auth-callout authorises
publishing under one's own id only, so the subject cannot be forged while the body can. That is
also why identity field names are rejected in payloads — an identity in the body would be a claim,
and the subject already carries the fact.

### Why the two planes are separate subject tokens

Not cosmetic. The command service's subscription ends in `>`, and that `>` would swallow the
queries too if they shared the `{service}` token. Two queue groups over overlapping subjects
deliver each message to **both** subscriptions, two replies arrive at the same inbox, and a plain
`request()` returns the first and **discards the second in silence**. Sharing a process does not
help; the overlap is in the subject. With a distinct token it cannot happen, because subject
tokens are compared whole.

A related trap when you subscribe yourself: `*` in a NATS subject matches **one whole token**. It
is not a prefix wildcard, so `jiku-*` matches the literal token `jiku-*` and never `jiku-queries`.

## The inbox

```text
_INBOX.<lowercase(base32(sha256(userId))[0..16])>
```

RFC 4648 alphabet, no padding, 16 characters — 80 bits, and free of `.`, `*` and `>`, none of
which may appear in a subject token.

The auth-callout grants `sub.allow: _INBOX.{{user_id_hash}}.>` and **nothing else**. It computes
this hash independently, on its side, with no channel to the client. If the two disagree, the
reply is published to a subject the client is not subscribed to and:

- the request times out after the full window,
- no permissions error reaches the caller,
- the violation is logged by the **NATS server**.

`test/fixtures/inbox-vectors.json` pins hashes **observed from a running callout** — captured, not
computed here, because a value generated by this implementation would only prove the code agrees
with itself.

The hash hides nobody — the user id is already raw in every subject. It exists because the inbox
needs one opaque, fixed-length token.

## The envelope

Every endpoint on both planes answers the same shape:

```jsonc
{ "status": "success", "data": { … } }

{ "status": "failure",
  "errorCode": "invalid_fields",
  "errorMessage": "…",
  "errorDetails": { "field": "filter", "value": "nope", "allowed": ["id", "projectId"] } }
```

On a failure the envelope travels in the **body**. The `Nats-Service-Error` headers are added
alongside it, never as a replacement — so the body is always the authority, and the micro
transport's 500 is not the error's status.

`errorDetails` is the structured half, so a caller never parses `errorMessage` with a regex. The
`allowed` list is the resource sheet's, **by reference** — which is exactly what makes
`meta.describe` verifiable against the validator. Unknown keys are preserved, so a field core
starts sending tomorrow is not lost.

## Reads

### The six levers

```jsonc
{
  "filter":  { … },
  "sort":    ["-createdAt"],
  "fields":  ["id", "title"],
  "include": ["project"],
  "page":    { "limit": 20, "cursor": "…" },
  "count":   true
}
```

Any other top-level key is `invalid_fields`, and so is any of the eleven forbidden identity names.

### Filters

The operator is decided by the **shape** of the value, and the comparison by its **type**:

| Shape                    | Operator                                         |
| ------------------------ | ------------------------------------------------ |
| `15`                     | equality                                         |
| `["a", "b"]`             | IN                                               |
| `{"not": …}`             | negation                                         |
| `{"gte": x, "lt": y}`    | range (`gt`, `gte`, `lt`, `lte`)                 |
| `{"key": k, "value": v}` | containment, where the sheet declares `contains` |

`{"projectId": "15"}` is **not** the same request as `{"projectId": 15}`. Anything whose input is
text has to consult the contract to type its values — `parseFilter` does, given a resource.

Today `requirements.tag` is the only containment filterable.

### Pagination

The reply's `page` block:

```jsonc
{ "limit": 20, "returned": 3, "cursor": "eyJ2IjoxLC…", "total": 97 }
```

- `limit` is the **effective** limit. A value above the resource's `maxLimit` is clamped
  **silently** — success, not failure — so this is the only place to learn the real ceiling.
- `returned` can be **fewer than `limit`** because of a byte budget: the engine cuts the page
  before the reply exceeds what NATS accepts and emits the cursor at the cut.
- `cursor` is absent on the last page. **Its absence is the only end-of-collection signal.**
  There is no `hasMore`, because two ways of saying the same thing eventually disagree.
- `total` appears only when `count` was requested. `count: true` costs a second query over the
  whole universe of the filter; `count: "only"` returns the total and does not run the rows query.

A cursor is a **keyset** cursor and is valid only for the exact filter and sort it was minted for.
Anything else answers `invalid_cursor`.

Iterating is not a snapshot: each page is its own query, so a record inserted between pages may
appear and one deleted may vanish. What the keyset guarantees is that no row is **skipped** for a
stable ordering, which is the property a full sweep needs.

### Deny-by-default

Every resource declares five closed lists. A name that is not in one of them **does not exist** —
it comes back as `invalid_fields` with `errorDetails`, never as a silently ignored lever. An
ignored filter would return _more_ data than was asked for, which is the worst failure mode a read
contract has.

`meta.describe` projects the same structures the validator reads. There is no second copy, so
there is nothing to drift.

### Discriminated resources

`comments`, `activity` and `subscriptions` have **variants**. Their `base`, `includable` and
`filterable` arrive empty (as `null`); the real whitelists live per variant under the
discriminator field, `entityType`. `sortable` and `defaults` stay at the resource level.

On `comments.get` the discriminator is **mandatory**: the same id means different records under
different entity types, so there is nothing sensible to default to.

## Writes

The write plane is not the mirror image of the read plane.

|                                                  | Query                             | Command                                      |
| ------------------------------------------------ | --------------------------------- | -------------------------------------------- |
| Product roles (`admin`, `user`, `external-user`) | all 23                            | **none**                                     |
| Who is acting                                    | the subject, and only the subject | the **body** (`creator`, `editor`, `author`) |
| Forbidden payload keys                           | eleven identity names             | `actor`, and only `actor`                    |
| Delivery                                         | request/reply                     | request/reply, no JetStream, no retry        |

The two lists cannot be shared. Several commands take an identity as **domain data** rather than
as a claim about who is calling — `requirements.{id}.subscriptors.new` requires `userId` (who is
being subscribed), `worked-times.new` takes `personId` (whose hours these are). Applying the read
plane's list to writes makes those commands impossible to send, which is refusing what the server
accepts.

What stays forbidden on both is `actor`: the reserved identity envelope the dispatcher extracts
before validating. Only the api's own service user (core's `CORE_TRUSTED_PUBLISHER_ID`) may carry
it, and core answers `invalid_fields` to anybody else — deliberately reusing the read plane's code,
because it is literally the same rule on the other side.

## Timeouts, and the order they fire in

```text
PostgreSQL statement_timeout   8s   ← cuts first
NATS_QUERY_TIMEOUT_MS         10s
this client (default)         15s
```

The order is deliberate. The database cuts first, so a slow query comes back as `query_timeout`
with an explanation rather than as silence. A client timeout below 10s breaks that ordering and
turns an explained failure back into a mute one, which is why the default here sits **above** the
server's rather than below it.

## The error catalog

`invalid_fields`, `invalid_cursor`, `caller_not_authorized`, `unknown_caller`, `unknown_command`,
`query_timeout`, `internal_error`, the twelve `*_not_found` codes, and the business-rule codes the
command plane emits.

**The catalog is core's, and it grows.** As write rules move from the api into core, new codes
appear. Nothing in this client switches exhaustively on a code: an unrecognised one still arrives
as a `JikuFailure` with its `code` and `details` intact. Use `isCode`, never a `switch` with a
`default` that assumes it has seen everything.

Two gates are worth telling apart because they look alike and are not:

- **`caller_not_authorized`** — this caller may not run this method. Usually the wrong role for
  the plane.
- **`unknown_caller`** — the caller has no row in core's `users` table. That row is created from
  the authentication event the auth-callout publishes on connect. A different question entirely,
  and merging the two would erase the rule that an unknown caller gets an error rather than an
  empty list.

On a `get`, a `*_not_found` deliberately does **not** distinguish "does not exist" from "you may
not see it": answering a permission error would confirm to an external caller that the record
exists.
